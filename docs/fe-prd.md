# MAY.ONE 프론트엔드 PRD

- 작성일: 2026-09-27
- 최근 갱신: 2026-09-28
- 상태: 원본 기준 브랜드 홈페이지 구현 및 Vercel Production 배포 완료; 공식 도메인·운영 자료·전체 QA는 후속 확인 중
- 구현 작업: [fe-task.md](./fe-task.md)

## 1. 목적과 기준 문서

MAY.ONE의 살롱·교육·마켓과 미용인의 성장 구조를 소개하고, 방문자가 지점 예약·교육 신청·상품 구매·채용 지원·산학협력 문의로 이동할 수 있는 공식 홈페이지를 구축한다. Next.js로 구현하고 Vercel에 배포한다.

프론트엔드 프로젝트와 주요 경로가 구현되어 있으며, 현재 기본 Vercel 주소 [mayone-home.vercel.app](https://mayone-home.vercel.app)에서 Production 사이트를 제공한다. 이 개정은 기존 [mayone_homepage.html](../origin_source/mayone_homepage.html)을 브랜드 디자인과 홈페이지 카피의 단일 기준으로 삼아 기존 임시 방향을 교체한다. 예약·교육·채용·문의 등 운영 기능은 유지하되 실제 공개 여부는 자료 확정 상태에 따른다. 공개 가능한 홈페이지가 배포되어 있어도 공식 도메인과 미확정 운영 기능까지 완료된 것은 아니다.

- 원자료의 작성 메모, 미확정 운영정보, 매출·지점 수 등 검증되지 않은 수치는 공개하지 않는다.
- 제품 범위는 이 PRD, 구현 순서와 체크 상태는 `fe-task.md`에서 관리한다. 원고 전문은 콘텐츠 기준 문서를 참조해 중복 관리를 줄인다.

## 2. 목표, 이용자, 범위

### 2.1 제품 목표

1. 첫 화면에서 `MAY.ONE HAIR`, `HARU 미용사관학교`, `MAY.ONE MARKET`의 역할을 이해할 수 있다.
2. 고객은 지점을 찾고 해당 지점의 공식 예약 수단으로 이동할 수 있다.
3. 수강자는 실제 교육의 대상·내용·일정·비용·신청 안내를 확인할 수 있다.
4. 지원자와 기관 담당자는 필요한 정보를 확인하고 해당 공고·프로그램의 공식 접수 수단으로 이동할 수 있다.
5. 모바일에서도 동일한 정보와 행동에 접근할 수 있다.

### 2.4 초기 성공 기준

- 원본 HTML의 아홉 구역·문구·CTA 순서가 화면에 반영되고, 새 카피가 사이에 추가되지 않는다.
- 공개한 내부 링크와 외부 CTA에 빈 목적지·잘못된 대상 연결이 없다.
- 실제 자료가 없는 영역은 자료 준비 상태로 구분하며, 가상 교육·공고·후기를 실제 정보처럼 보여주지 않는다.
- 모바일 메뉴, 목록 검색·필터, 상세 직접 접근, 브라우저 뒤로 가기가 동작한다.
- 품질 기준과 배포 점검을 통과한다. 사업 전환율의 목표 수치는 실제 운영·측정 도입 후 정한다.

## 3. 정보 구조와 라우팅

### 3.1 공통 내비게이션

| 표시 | 메인에서 | 다른 페이지에서 |
| --- | --- | --- |
| MAY.ONE 로고 | `/#top` | `/` |
| SALON | `/#hair` | `/#hair` |
| HARU ACADEMY | `/#haru` | `/#haru` |
| MAY.ONE MARKET | `/#market` | `/#market` |
| RECRUIT | `/#recruit` | `/#recruit` |
| ABOUT US | `/#about` | `/#about` |

- 영문 메뉴에 한국어 설명 또는 접근 가능한 이름을 제공한다.
- 데스크톱은 한 줄 헤더, 좁은 화면은 햄버거 버튼과 사이드 패널을 사용한다. 메뉴가 깨지기 전에 접는다.
- 헤더는 상단 고정 또는 sticky 방식으로 유지한다. 앵커 대상은 헤더 높이만큼 스크롤 여유를 둔다. 메인에서 현재 해시와 같은 앵커를 다시 선택해도 해당 섹션으로 다시 이동한다.
- 앵커 정렬에는 일관된 스크롤 오프셋 하나만 적용한다. `scroll-padding`과 `scroll-margin`이 중복되어 섹션이 헤더 아래로 과하게 밀리지 않게 한다.
- 로그인·회원가입·MY 버튼과 검색 아이콘은 이번에 노출하지 않는다. 검색은 지점 목록 안에서 제공한다.

### 3.2 구현 경로

| URL | 역할 | 공개 조건 |
| --- | --- | --- |
| `/` | 브랜드 메인과 주요 콘텐츠 요약 | 기본 브랜드 원고 확정 |
| `/salon` | 전체 지점, 지점명 검색, 지역 필터 | 자료 미확보 시 준비 상태도 제공 |
| `/salon/[branchId]` | 지점·디자이너·스타일·방문·예약 안내 | 공개 가능한 지점 데이터 존재 |
| `/haru/classes` | 교육 목록, 분야·모집 상태 필터 | 자료 미확보 시 준비 상태도 제공 |
| `/haru/classes/[classId]` | 교육 내용·강사·일정·비용·신청 안내 | 공개 가능한 교육 데이터 존재 |
| `/haru/cooperation` | 공개 확인된 산학협력 프로그램·기관·문의 안내 | 실제 공개 자료가 있을 때만 표시하고 문의는 채널 확보 후 활성화 |
| `/recruit` | 성장 경로와 채용 목록 | 공고 미확보 시 준비 상태도 제공 |
| `/recruit/[jobId]` | 채용 조건·절차·지원 안내 | 공개 가능한 공고 데이터 존재 |
| `/about` | 원본 ABOUT US의 사업 연결 구조를 보충하는 소개 | 원본 HTML의 브랜드 문구만 사용 |
| `/privacy` | 개인정보처리방침 | 공식 문서 확보 시 제공 |
| `/terms` | 필요한 홈페이지 이용 안내 | 운영상 필요하고 공식 문서가 있을 때 제공 |
| 존재하지 않거나 미공개인 상세 URL | 404와 관련 목록 이동 | 임의 ID로 더미 상세를 생성하지 않음 |

상세는 기본적으로 독립 페이지로 구현해 공유·직접 접근·SEO를 지원한다. 상세 모달은 초기 필수 범위가 아니다. 정책 페이지 원문은 임의로 작성하지 않으며, 공식 외부 정책 페이지가 있으면 그 링크를 사용할 수 있다.

### 3.3 메인 콘텐츠 매핑

메인 콘텐츠 순서는 원본의 `히어로 → ONE BRAND. ONE SYSTEM. → MAY.ONE HAIR → MAY.ONE SYSTEM → HARU → MAY.ONE MARKET → RECRUIT → EVERYTHING IS CONNECTED. → 마지막 CTA`를 그대로 따른다. 기존 PRD의 추가 기획 섹션인 연혁·지점 요약·강사진·수강 일정·산학협력은 메인 랜딩에서 제거하고, 해당 정보가 확정되면 기존 독립 경로에서 제공한다. 헤더와 푸터의 고정 위치·접근성 기능은 유지하며 시각 스타일은 원본 HTML에 맞춘다.

| 순서 | 영역 / 앵커 | 원본 콘텐츠 | 구현 내용·주요 이동 |
| --- | --- | --- | --- |
| 1 | 히어로 `top` | SALON · EDUCATION · MARKET | MAY.ONE, 대표 문구, 세 사업, 살롱·HARU·마켓 CTA |
| 2 | 브랜드 구조 `brand-story` | ONE BRAND. ONE SYSTEM. | 살롱에서 비즈니스까지 이어지는 5단계 성장 흐름 |
| 3 | 살롱 `hair` | MAY.ONE HAIR · BEAUTY BEYOND STYLE | 원본 소개 문구, CSS 브랜드 비주얼, `/salon`·채용 이동 |
| 4 | 시스템 `system` | MAY.ONE SYSTEM | EDUCATION·CONSULTING·MARKETING·MANAGEMENT·GROWTH 5개 카드 |
| 5 | 교육 `haru` | HARU HAIR PROFESSIONAL ACADEMY | Learn. Grow. Lead., 교육 원칙 4개·기본 교육 분야 5개, `/haru/classes` |
| 6 | 마켓 `market` | MAY.ONE MARKET | 원본 소개 문구와 확인된 스토어·상품 링크. 목적지 미확인 CTA는 비활성 |

브랜드 카피는 원본 파일의 문구를 그대로 사용한다. 원본의 `href="#"`는 실제 내부 경로로 연결하거나 자료 미확보 시 비활성 상태로 바꾸며 빈 목적지를 만들지 않는다. 이미지 자료가 없으면 원본의 CSS 기반 visual 패널을 비사진형 임시 비주얼로 사용하고 운영 사진이나 공식 로고처럼 표현하지 않는다.

## 4. 기능 요구사항

### FE-01. 공통 레이아웃과 이동

- 공통 헤더·푸터, 본문 바로가기, 페이지 제목·관련 목록 이동을 제공한다. 헤더·푸터의 카피와 시각 표현은 원본 HTML에 맞춘다.
- 모바일 메뉴는 열기·닫기, 오버레이, Escape 닫기, 포커스 이동·복귀, 포커스 제한, 본문 스크롤 잠금을 지원한다.
- 메뉴를 선택하거나 페이지가 바뀌면 패널을 닫는다. 현재 페이지·메뉴 상태를 색상 외의 방식으로도 표현한다.
- 푸터에는 원본의 MAY.ONE 워드마크, `SALON · EDUCATION · MARKET`, 저작권 문구를 표시한다. 원본에 없는 연락처·SNS·정책·빠른 이동 링크를 임의로 덧붙이지 않는다.

**완료 기준:** 모든 공개 페이지에서 메뉴와 푸터를 사용할 수 있고, 키보드로 메뉴를 열고 닫은 뒤 본문 또는 시작 버튼으로 자연스럽게 이동한다. 메인 앵커는 같은 링크를 반복 선택해도 이동하며 고정 헤더 바로 아래에 정렬된다.

### FE-02. 메인 브랜드 랜딩

- `mayone_homepage.html`의 원문 카피와 섹션 순서를 반영한다. 임의로 새 연혁·산학협력·강사진·교육 일정·후기 섹션을 랜딩에 추가하지 않는다.

**완료 기준:** 원본 랜딩의 아홉 구역과 카피 순서가 일치하고, 세 사업의 역할과 다음 행동이 첫 화면에서 읽힌다.

### FE-03. 지점 목록과 상세

- 원고의 12개 지점명은 자료 관리의 초기 후보로 등록한다. 현재 운영 지점 수나 주소·지역을 추정하지 않는다.
- 목록에서는 공개 가능한 지점만 표시하고, 지점명과 확정 지역에 대한 검색·필터를 제공한다. 검색과 지역 선택은 함께 적용한다.
- 검색 결과가 없으면 지점명이나 지역을 바꾸도록 안내한다. 이 페이지에는 조건 초기화 버튼을 두지 않으며, 지역 필터는 실제 확정 지역값으로 생성한다.
- `/salon`은 지점마다 넓은 세로형 정보 블록을 배열한다. 지점명·지역, 주소, 매장 전화, 운영시간·휴무, 주차, 찾아가는 길, 매장 편의 정보와 예약 CTA를 확인된 범위에서 표시한다.
- 지점별 네이버 예약 CTA는 공식 예약 URL이 확인된 경우에만 활성화한다. 네이버 플레이스 URL은 출처·운영 정보 관리에 사용하고, 별도 플레이스 링크는 목록에 표시하지 않는다.
- 정보 수집이 어려운 동안 지점 상세 보기와 `/salon/[branchId]` 경로는 임시 비활성화하고 사이트맵에서도 제외한다. 상세 정보를 확보하면 상세 화면을 재개한다.
- 실제 지점 사진이 확인된 경우에만 사진을 표시한다. 사진 자료가 없으면 빈 갤러리나 임의 이미지를 만들지 않는다.
- 상세는 지점 소개 → 방문 안내 → 디자이너 → 스타일 → 예약 순으로 구성한다. 사진·디자이너·스타일이 없는 선택 영역은 숨긴다.
- 예약 URL이 없는 지점은 안내와 실제 대체 문의 수단을 사용한다. 디자이너 예약 URL이 없으면 해당 디자이너 전용 예약 버튼을 만들지 않는다.

**완료 기준:** 검색·지역 필터와 예약 링크가 공개된 지점에 정확히 적용된다. 현재 비활성화한 상세 경로는 404이며, 미공개 또는 없는 ID도 공개되지 않는다.

### FE-04. HARU 소개와 교육 목록·상세

- BASIC / PRACTICE / FIELD / GROWTH의 4개 원칙과 CUT / PERM / COLOR / CONSULTING / SALON WORK의 5개 교육 체계를 소개한다.
- 교육 목록의 분야는 실제 공개 강의에서 생성한다. 원고의 AI·마케팅·블로그·세무·경영 등을 현재 개설 강의로 오해하게 표시하지 않는다.
- 분야·모집 상태 필터를 함께 적용하고 초기화할 수 있다. 모집 예정·모집 중·마감·종료 상태를 텍스트로 표시한다.
- 상세는 교육 이미지·제목·상태 → 강사 → 교육 내용·대상·커리큘럼 → 일정·장소 → 비용·포함 내역·준비물 → 신청·결제·취소 안내 → 신청·문의 순이다.
- 신청 활성화에는 확정 일정·장소·비용·신청 URL·취소 안내가 필요하다. 무료 교육은 확정된 경우에만 `무료`로 표시한다.
- 모집 상태와 날짜는 별도로 관리한다. 마감·종료·기한 경과에는 신청 CTA를 활성화하지 않는다. 실제 잔여석 연동이 없으므로 잔여석 숫자는 제공하지 않는다.
- 날짜·시간은 명시적인 시간대와 함께 저장하고 한국 이용자에게 `Asia/Seoul` 기준으로 표시한다.

**완료 기준:** 선택한 교육의 판단 정보와 공식 신청 수단이 일치하며, 강의 자료 미확보·신청 가능한 강의 없음·필터 결과 없음·마감·종료를 구분한다.

### FE-05. 산학협력

- 산학협력은 기존 독립 경로에 유지하되 원본 랜딩의 메인 흐름에는 넣지 않는다.
- 확정된 프로그램·기관·문의 자료가 없으면 제안 프로그램 이름이나 학교·협약 관계를 실제 정보처럼 소개하지 않고 준비 상태만 표시한다.
- 상세에는 협력 대상, 협의 항목, 프로그램, 확정 사례, 공식 문의 채널을 제공한다.
- 기관명·로고·협약·성과는 현재 공개 가능한 자료를 확보한 경우에만 표시한다.
- 공식 문의 채널이 없으면 문의 준비 안내를 제공한다. 홈페이지 안에서 개인정보를 입력받지 않는다.

**완료 기준:** 프로그램을 이해하고 확정된 담당 채널로 이동할 수 있다. 채널 미확보 시 제출 버튼이나 접수 완료를 표시하지 않는다.

**완료 기준:** 공식 스토어 CTA가 확인된 주소로 이동하고 외부 서비스 이동을 예측할 수 있다. 대표 상품의 목적지·판매 상태 확인 전에는 해당 CTA를 공개하지 않는다.

### FE-07. 채용 목록과 상세

- 성장 경로 4단계를 기간·승급·매출 보장 없이 소개한다.
- 목록에는 실제 공고의 제목·지점·직무·경력·모집 상태·마감일을 제공한다. 마감일이 없는 확정 상시 모집은 `상시 모집`으로 구분한다.
- 상세에는 업무, 자격·우대, 실제 근무지, 근무 조건, 급여 안내, 전형, 제출 자료, 지원 URL·문의처를 제공한다.
- `채용공고 보기`는 목록, `입사지원하기`는 선택 공고의 공식 지원 수단으로 연결한다.
- 지원 URL이 없거나 마감된 공고는 지원 CTA를 활성화하지 않는다. 공고가 없는 상태를 상시 채용으로 대체하지 않는다.

**완료 기준:** 공고의 지점·조건·상태·지원 대상이 일치하며, 공고 미확보와 확인된 공고 없음 상태를 구분한다.

### FE-08. 브랜드 상세와 선택 콘텐츠

- `/about`는 원본 About Us 메시지와 HARU ACADEMY·MAY.ONE HAIR·MAY.ONE MARKET의 3개 연결 구조를 사용한다.
- 랜딩에 없는 성장 연혁·성과·인원·지점 숫자를 채우지 않는다. 후속 브랜드 콘텐츠가 승인되면 별도 자료 범위와 함께 개정한다.
- 강사진, 운영진, 협력 사례, FAQ는 실제 정보·답변을 확인한 경우에만 노출한다. 화면의 필수 공간을 채우기 위해 내용을 만들지 않는다.
- 후기·시술 전후 비교는 초기 필수 콘텐츠가 아니다. 후속 추가 시 실제 자료·조건·공개 범위를 확보한다.

**완료 기준:** `/about`가 원본 About Us의 3개 사업 연결 구조를 사용하고, 확정되지 않은 추가 콘텐츠는 노출하지 않는다.

### FE-09. 콘텐츠 공개와 CTA 상태

| 상황 | 화면 동작 |
| --- | --- |
| 자료를 아직 받지 못함 | `지점 정보를 준비 중입니다.`, `교육 일정을 준비 중입니다.`, `채용 정보를 준비 중입니다.` 등 해당 영역 안내 |

- 외부 행동 URL은 중앙에서 관리하고 같은 CTA의 이름과 목적지를 통일한다.
- 자체 접수, 성공 토스트, 임시 저장에 의한 신청 완료, 더미 로그인은 구현하지 않는다.

**완료 기준:** 자료·운영·필터·오류 상태가 구분되고, 모든 활성 행동에 유효한 목적지가 있다.

| 폭 | 처리 |
| --- | --- |
| 800px 미만 | 원본처럼 한 열, 20px 좌우 여백, split·카드 열 세로 쌓기, CTA 줄바꿈 |
| 800–1023px | 레이아웃에 따라 split을 유지할지 한 열로 전환할지 콘텐츠 폭으로 결정 |
| 1024px 이상 | 약 1180px 콘텐츠 폭, 소개 좌우 분할, 원본의 3·4·5열 카드 구성 |

- 모바일 성장 흐름은 화살표와 단계를 자연스럽게 줄바꿈하고 한국어 설명 순서를 유지한다.
- 긴 지점명·강의명·직무·주소는 줄바꿈한다. 판단에 필요한 정보는 말줄임표만으로 숨기지 않는다.
- 사진을 받으면 일정한 비율과 `object-position`을 확인해 인물·시술 초점이 잘리지 않게 한다.
- 구현 QA 폭은 320, 375/390, 768, 1024, 1440px이다. 브레이크포인트는 실제 콘텐츠가 깨지는 지점에 맞춰 조정할 수 있다.

## 6. 기술 설계 기준

### 6.1 프로젝트와 렌더링

- 저장소 루트에 Next.js 프로젝트를 구성하고 `docs/`, `origin_source/`를 유지한다. 원자료 전체를 `public/`에 복사하지 않는다.
- App Router + TypeScript strict를 사용한다. 구현 시작 시 지원되는 안정 버전과 호환 React·Node.js·패키지 매니저를 확인해 버전과 lockfile을 고정한다.
- 정적 소개와 상세 본문은 Server Component를 기본으로 하고, 모바일 메뉴·검색·필터·기한에 따른 CTA 등 상호작용만 작은 Client Component로 분리한다. [Next.js Server/Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)
- 초기 콘텐츠는 정적 생성이 가능한 구조로 제공하고, 공개 상세 ID는 `generateStaticParams`로 생성한다. 미공개·없는 ID는 데이터 조회와 라우트에서 404로 처리한다. [generateStaticParams](https://nextjs.org/docs/app/api-reference/functions/generate-static-params)
- Vercel의 일반 Next.js 배포를 사용한다. 초기 화면을 정적으로 제공해도 `output: 'export'`를 필수로 하지 않는다. 후속 인증·서버 기능 도입을 위한 별도 정적 호스팅 구조를 만들지 않는다.
- 글로벌 CSS는 토큰·리셋·공통 규칙, 컴포넌트 스타일은 CSS Modules를 기본으로 한다. 대규모 UI 프레임워크·전역 상태 관리·클라이언트 데이터 캐시를 초기 필수 의존성으로 도입하지 않는다.
- 목록 검색·필터는 Client Component의 상태로 처리한다. 주소에 필터 상태를 저장하는 기능은 초기 필수가 아니다.
- 새 캐시 기능·실험 기능은 초기 필수가 아니다. 교육·공고 데이터가 없는 경우에도 정상 빌드되는 구성을 선택한다.

### 6.2 권장 파일 구성

```text

  components/

    salon/, haru/, recruit/
  content/        # 브랜드 원고, 지점, 강사, 교육, 공고, 링크
  types/          # 공개 콘텐츠 타입
```

## 7. 콘텐츠 모델과 운영

### 7.1 데이터 분리

| 모델 | 핵심 필드 |
| --- | --- |
| 공통 | 안정된 `id`, `publicationState: draft/published`, 확인일, 이미지·alt, 필요한 공개 정보 |
| 브랜드·공통 링크 | 원고, 메뉴·CTA, 공식 마켓·상품·SNS·목적별 문의·정책 URL, 운영 주체 |
| 지점 | 공식 지점명, 지역, 주소, 운영 여부, 운영시간·휴무, 연락처, 예약 URL, 방문 안내 |
| 디자이너·스타일 | 소속 지점 ID, 이름·직책·분야·소개·예약 URL / 실제 사진·스타일명·시술 분야·디자이너 ID |
| 강사 | 이름·직책·분야·소개·이력·공개 가능한 사진 |
| 교육 | 제목·분야·강사 ID·내용·대상·커리큘럼·일정·장소·비용·준비물·취소 안내·모집 상태·신청 URL·문의 |
| 채용 | 공고명·지점 ID·직무·자격·업무·조건·전형·모집 상태·마감일·지원 URL·문의 |
| 산학협력 | 프로그램·협의 항목·담당 채널, 확인된 기관·프로그램별 사례 |

- 공개 상태와 모집 상태는 별개다. 공개된 종료 교육·마감 공고는 상세를 읽을 수 있어도 신청·지원은 불가능하다.
- 원고의 지점·강사 후보는 확인 전 `draft`로 관리한다. Production의 목록·상세·사이트맵·메타데이터·클라이언트 전달 데이터에는 포함하지 않는다.
- 개발·검수용 예시 데이터는 별도 fixture로 두고 Production 콘텐츠에 섞지 않는다. Preview에서는 예시임을 표시하고 검색 노출을 막는다.
- 목록별 자료 상태는 `pending`(자료 미확보) / `confirmed`(운영팀 확인)로 관리한다. `confirmed` 상태의 빈 배열과 `pending`을 다른 문구로 처리한다.
- 선택 필드는 없는 영역을 숨긴다. 공개 필수 필드 누락·잘못된 ID 참조·중복 ID·잘못된 URL·잘못된 일정은 콘텐츠 검증에서 잡는다.
- 지점 공개에는 공식 명칭·지역·주소·운영 여부 확인이 필요하다. 예약 URL은 예약 활성화 조건으로 별도 관리한다.
- 신청 가능한 교육의 필수 항목은 FE-04, 지원 가능한 공고의 필수 항목은 FE-07을 따른다. 자료 준비 상태의 미완성 항목을 완성된 강의·공고처럼 공개하지 않는다.

### 7.2 갱신과 기한 관리

- 콘텐츠 수정 → 공개 상태·필수값 검증 → Preview 확인 → Production 재배포 순으로 갱신한다. 초기에는 CMS나 자동 동기화가 없다.
- 데이터와 외부 URL은 화면에 흩어 놓지 않고 조회 함수와 CTA 판단 규칙을 통해 사용한다. 후속 저장소 변경 시 조회 계층을 교체할 수 있는 정도로 분리한다.
- 교육·공고의 모집 상태는 운영팀이 확정한다. 종료·마감일 경과는 현재 시각으로 CTA를 추가 제한하고, 날짜만으로 모집 중 상태를 자동 생성하지 않는다.
- 정적 빌드 시점에만 기한을 판단하면 배포 이후 오래된 버튼이 남을 수 있다. 기한이 있는 신청·지원 CTA는 브라우저 현재 시각도 확인하고, 확인 전에는 안전한 비활성 상태를 유지한다. 페이지를 오래 열어둔 경우에도 기한 도달·탭 복귀·클릭 직전에 다시 판단한다.
- 이 제한은 실시간 정원·접수 보장을 의미하지 않는다. 외부 서비스의 실제 접수 상태가 최종 기준이며, 운영 담당자는 상태 변경 시 콘텐츠도 갱신한다.

## 8. 비기능 요구사항

### NFR-01. 접근성

- `lang="ko"`, 페이지당 하나의 대표 h1, 논리적인 제목 계층, header/nav/main/footer 구조를 제공한다.
- 모든 메뉴·CTA·필터를 키보드로 사용할 수 있고, 명확한 `:focus-visible`을 제공한다.
- 일반 텍스트 대비 4.5:1, 큰 텍스트 3:1을 목표로 점검한다. 큰 텍스트의 구분은 WCAG 기준을 따른다. 오류·모집 상태·현재 메뉴를 색상만으로 표시하지 않는다. [WCAG Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- 버튼·메뉴 터치 영역 최소 44×44px, 검색 입력의 항상 보이는 라벨, 상태 변화의 적절한 보조기술 안내를 제공한다.
- 의미 있는 이미지에는 실제 내용에 맞는 alt, 중복 장식에는 빈 alt를 사용한다.
- 200% 확대, `prefers-reduced-motion`, 모바일 안전 영역, 메뉴 포커스와 고정 헤더 가림을 확인한다.

### NFR-02. 성능과 이미지

- 실제 공개 이미지로 QA하며 `next/image`, 명시적 크기 또는 고정 비율 컨테이너와 `sizes`를 사용한다. [Next.js Image Optimization](https://nextjs.org/docs/app/getting-started/images)
- 첫 화면의 주요 이미지는 적절히 우선 로딩하고 나머지는 지연 로딩한다. 외부 이미지가 필요하면 허용 출처를 제한한다.
- PDF 스크린샷이나 큰 원본을 그대로 대표 웹 이미지로 사용하지 않는다. 얼굴·머리·시술의 중요한 초점을 검수한다.
- release 빌드의 모바일 Lighthouse 성능 90 이상을 목표로 하고, 접근성·SEO 95 이상을 목표로 한다. 결과와 주요 미달 원인을 기록하고 필요한 개선 후 재측정한다.
- LCP 2.5초 이하, CLS 0.1 이하를 목표로 관리한다. INP 200ms 이하는 운영 이후 실제 사용자 측정 목표이며, 초기 실험실 측정만으로 충족을 주장하지 않는다. 실사용 평가는 모바일·데스크톱을 구분해 방문의 75번째 백분위수를 기준으로 한다. [Google Core Web Vitals](https://web.dev/articles/vitals)

### NFR-03. SEO와 공유

- Next.js Metadata API로 페이지별 title·description·OG를 구성한다. 메인 브랜드명·대표 문구는 원본 HTML을 기준으로 하고, 상세의 운영 정보는 확정 콘텐츠만 사용한다. [Metadata and OG images](https://nextjs.org/docs/app/getting-started/metadata-and-og-images)
- 지점·교육·공고의 주요 판단 정보는 이미지에만 넣지 않고 검색 가능한 HTML 본문에 제공한다.
- 공식 도메인 확정 후 canonical·metadataBase·사이트맵 주소를 설정한다. 임시 도메인을 공식 주소로 고정하지 않는다.
- Production 사이트맵에는 공개 가능한 페이지만 포함한다. 정책·상세 데이터가 없으면 해당 URL을 포함하지 않는다.
- Preview는 `noindex` 처리하고 robots에서도 크롤링을 제한한다. `noindex`는 접근 통제가 아니므로 실제 개인정보·비공개 자료를 Preview에도 올리지 않는다.
- 공식 로고·대표 이미지·한국어 메시지를 포함한 공유 이미지와 favicon을 제공한다.

### NFR-04. 유지보수와 안정성

- `lint`, TypeScript 검사, 콘텐츠 검증, 중요한 상태 테스트, Production build가 통과해야 한다.
- 테스트는 공개 필터링, 검색·필터 조합, 신청·지원 CTA 조건, 기한 경과, 404, 모바일 메뉴 등 실제 실패 위험에 집중한다.
- 정상 공개 경로에 런타임 오류·콘솔 오류·깨진 이미지·빈 링크가 없어야 한다.
- `.env.example`에는 현재 필요한 공개 사이트 설정만 문서화한다. 실제 비밀값·소셜 키·Supabase 키는 이번 프로젝트에 넣지 않는다.

## 9. Vercel 배포와 공개 기준

### 9.1 배포 방식

- 저장소를 Git으로 관리하고 Vercel 프로젝트에 연결한다. 구현 브랜치는 Preview, 지정한 운영 브랜치는 Production에 연결한다. [Vercel Git deployments](https://vercel.com/docs/git)
- Development·Preview·Production의 설정을 구분하고 같은 Node.js·패키지 매니저·빌드 명령을 사용한다. [Vercel environments](https://vercel.com/docs/deployments/environments)
- 사이트 공식 URL과 검수 데이터 사용 여부는 환경별로 관리한다. 검수 데이터는 명시적으로 선택한 비운영 환경에서만 사용한다.
- Preview의 실제 배포 주소에서 직접 상세 접근, 새로고침, 404, 이미지, 앵커, 외부 링크, SEO와 모바일 메뉴를 확인한다.
- 배포한 버전과 알려진 자료 공백, 콘텐츠 수정 절차, 이전 정상 배포로 되돌리는 절차를 기록한다.

현재 구현은 GitHub `TeusEE/mayone_web`의 `main` 브랜치에 push되며, Vercel 프로젝트 `mayone-home`의 Production은 `https://mayone-home.vercel.app`에서 제공된다. 현재는 Git push만으로 Vercel이 자동 배포되지 않아 CLI 배포를 사용한다. Vercel Git 자동 연동과 별도 공식 도메인 설정은 남은 작업이며 자세한 상태는 [fe-task.md](./fe-task.md)에 기록한다.

| 단계 | 완료 기준 |

| 채용 지원·산학협력 문의 공개 가능 | 해당 공고·프로그램의 실제 조건·담당 채널·지원/문의 수단 확인 |

자료가 없는 경우 화면 구현 완료와 기능 공개 완료를 같은 상태로 기록하지 않는다. 초기 브랜드 공개는 가능하지만 준비 중 영역을 실제 예약·신청 서비스의 완료로 간주하지 않는다.

## 10. 후속 인증·Supabase 계획 — 구현 보류

| 예정 사항 | 현재 상태 |
| --- | --- |
| 카카오 회원가입·로그인 | 후속 요구사항으로만 기록 |
| 네이버 회원가입·로그인 | 후속 요구사항으로만 기록 |
| Supabase 사용 | 후보; 도입 여부 미확정 |
| 로그인 UI·세션·콜백·회원 모델 | 설계·구현 보류 |
| 회원 전용 권한·교육/지원 이력 | 제품 범위 미확정 |

- 이번 작업에는 SDK 설치, 소셜 앱 등록, OAuth 설정, Supabase 프로젝트 생성, DB/RLS/Storage 설계, 인증 환경변수, 콜백 라우트가 없다.
- 모든 공개 콘텐츠와 외부 행동은 비회원으로 이용할 수 있게 구현한다.
- 추후 착수할 때 공급자별 지원 여부와 연동 방법을 공식 문서로 확인한다. 특히 네이버와 카카오가 후보 서비스에서 같은 방식으로 지원된다고 전제하지 않는다.
- 이번에 필요한 확장 준비는 UI와 콘텐츠 조회의 분리뿐이다. 사용하지 않는 인증 추상화나 가짜 회원 상태를 미리 만들지 않는다.
